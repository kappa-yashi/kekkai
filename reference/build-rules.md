# kekkai build rules

Rules for whoever (or whatever) writes the code of a static site that will be
checked with `kekkai`. Paste this into the assistant at the start of the
project, or keep it next to the repo (git-ignored or not: it describes a
method, not your setup). Every rule maps to a check; a site built by these
rules passes `kekkai ./repo`, `kekkai ./dist` and `kekkai <url>` with nothing
left to fix.

Reference stack: Astro, static output, Cloudflare Pages (or any host that
applies a `_headers` file). Most rules are stack-agnostic.

## The principle

What the site **does** is public. How it is **built** is nobody's business.
A static build with no server, no accounts and no admin is the security
property; do not trade it away for a feature.

## DON'T

- No inline `<script>` with executable code. The only inline script allowed is
  `type="application/ld+json"`.
- No `style=""` attributes and no `<style>` tags in the output (Shiki and
  similar highlighters emit `style=""` on every token: turn them off or use a
  class-based highlighter).
- No inline event handlers (`onclick=`, `onload=` …), in HTML or in SVG.
- No `'unsafe-inline'`, `'unsafe-eval'`, `*`, `https:` or `data:` in
  `script-src`. Never loosen the CSP to make a third party work.
- No scripts, stylesheets or fonts from public CDNs (unpkg, jsdelivr, cdnjs,
  Google Fonts, esm.sh). Self-host. If a vendored bundle `import()`s from a CDN
  at runtime, vendor those helpers too and patch the loader.
- No tag manager or analytics host in `script-src`; if analytics is required,
  use a first-party or server-side setup.
- No CSP under `/*` in `_headers` when any path has its own CSP (the browser
  enforces the intersection and the narrower one wins).
- No `<meta>` CSP carrying `frame-ancestors` or `report-uri` (ignored there).
- No `Disallow: /admin` in `robots.txt`; it advertises the path.
- No admin/CMS folder named `admin`, `cms`, `studio`, `backend`, `dashboard`.
- No email address in JSON-LD, `llms.txt`, feeds, sitemaps, `humans.txt` or
  any non-HTML file. In HTML, the address only inside the `mailto:` href.
- No developer comments in the shipped HTML, no comments in served config
  files (a CMS `config.yml` is public).
- No `<meta name="generator">`, no `X-Powered-By`, no source maps in the
  output, no `sourceMappingURL` comments, no `package.json`, lockfiles,
  `.env*`, `*.config.*`, `README.md` or `.git` in the output.
- No local filesystem paths (`/home/x/`, `C:\Users\x\`) in the output.
- No staging, preview or `*.pages.dev` hostnames anywhere public.
- No secret value, and no description of its shape ("starts with `shpat_`"),
  in code, comments, docs, commits, issues or chat.
- No docs that describe *how* security is set up: policies, scopes, login
  method, app names, account emails. Docs say *where* it is configured.
- No `CLAUDE.md`, `AGENTS.md`, `.claude/`, `.cursor*`, `copilot-instructions`
  tracked in the repo; no `Co-Authored-By: <assistant>` or "Generated with …"
  trailers; no "built with <assistant>" credit in output or docs.
- No one-off scripts that write into CMS-managed content folders left in the
  repo.
- No `_redirects` rule whose destination host comes from the request
  (`https://:splat`), and none pointing at a staging host.
- No `Cache-Control` on `version.txt` other than `no-store`.

## DO

- Astro config:
  `build: { inlineStylesheets: 'never' }`,
  `vite: { build: { assetsInlineLimit: 0 } }`,
  `markdown: { syntaxHighlight: false }` (or a class-based highlighter).
- Code that must run before first paint (theme restore) lives in
  `public/<name>.js`, loaded with `<script is:inline src="/<name>.js?v=<hash>">`;
  validate everything it reads from `localStorage` before applying it.
- Dynamic styling through data attributes + CSS, or the CSSOM from a bundled
  script; editor-controlled colours generated into a CSS file at build.
- One CSP per path group, from `default-src 'none'` upwards, each exception
  scoped to one directive and one origin. `object-src 'none'`,
  `base-uri 'none'` (or `'self'`), `form-action 'none'` (or `'self'`),
  `frame-ancestors 'none'` as a **header**.
- `_headers` generated by a post-build script from the built HTML: one CSP
  block per route group derived from `dist/**/*.html`, cache rules for
  `/_astro/*` and fonts, `version.txt` as `no-store`, the CMS block with its
  own CSP + `no-store` + `X-Robots-Tag: noindex`. Fail the build if
  `public/_headers` exists. `kekkai init` scaffolds this script.
- Security headers on every response: HSTS (`max-age` ≥ 1 year,
  `includeSubDomains`; decide `preload` on purpose), `X-Content-Type-Options:
  nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`
  (`strict-origin-when-cross-origin` or `no-referrer`), `Permissions-Policy`,
  `Cross-Origin-Opener-Policy: same-origin`,
  `Cross-Origin-Resource-Policy: same-origin`, and remove
  `Access-Control-Allow-Origin` (`! Access-Control-Allow-Origin`), then verify
  it is gone on the live response.
- A build fingerprint: `version.txt` + `<meta name="build">` from
  `package.json` version and `CF_PAGES_COMMIT_SHA` (or the git short hash).
- `www` is the primary host; the apex 301s to it (cookie isolation from
  subdomains, CNAME-able for CDN and failover).
- Absolute `<link rel="canonical">` on every page; `robots.txt` with no private
  paths; sitemap listing the final URLs (trailing slash included).
- Every cross-origin resource that cannot be self-hosted carries
  `integrity="sha384-…" crossorigin="anonymous"`.
- CMS (Decap, Sveltia …): self-hosted pinned bundle, unguessable folder name
  kept in a build-time-only constant, its own CSP, `no-store`, `noindex`
  header **and** meta, Cloudflare Access on that path, private content
  repository, fine-grained expiring token or your own OAuth Worker; strip
  comments from `config.yml` at build; links in content get
  `rel="noopener noreferrer"`.
- `.gitignore`: `.env`, `.env.*`, `.dev.vars`, `node_modules/`, `dist/`,
  `.astro/`, `*.local.json`, `.claude/`, `CLAUDE.md`, `CLAUDE.local.md`,
  `AGENTS.md`, `.cursor/`, `.cursorrules`.
- Before `npm install <pkg>`, before choosing a CMS, a builder or a
  third-party platform: `kekkai check <name>[@version]`. It answers from the
  pwn.watch feed — open incidents, past supply-chain compromises, fixed
  versions. Adopt with the history in view; a clean answer is "no news", not
  "safe".
- Dependencies pinned by a lockfile and kept out of known incidents: every
  `kekkai ./repo` run matches the lockfile against the pwn.watch feed
  (patch-now, breach, supply-chain); a ✖ there means upgrade before anything
  else ships. After a supply-chain incident, rotate every token the build
  could have read.
- Commits authored by the project owner, without assistant trailers;
  production builds from `main` only, through a merge.
- Before every release: `kekkai ./repo --forbid <other brands, staging hosts>`,
  `kekkai ./dist --admin <cms folder>`, deploy, `kekkai https://<site>
  --admin <cms folder> --accept-edge-inline`. Fix in the guide's order
  (headers → CSP → fingerprint → dashboard → leaks → CMS → repo), then read the
  live response again. The live response is the only truth.

## When the static site has a backend (Medusa)

- `medusa-config`: every secret from the environment, **no** `\|\| "fallback"`;
  CORS lists with exact origins (never `/http.*/` or `*`); `databaseUrl`
  from the environment; `rejectUnauthorized` left unset unless the DB
  provider requires otherwise.
- Admin dashboard either disabled on the API host (`admin.disable`) and
  deployed privately, or behind an access layer; never on the storefront's
  origin.
- Custom route groups outside `/store`, `/admin`, `/auth` get an explicit
  entry in `src/api/middlewares` (`authenticate()` or a written "public"
  decision).
- Storefront builds carry the production `NEXT_PUBLIC_MEDUSA_BACKEND_URL` and
  only the `pk_` publishable key; an `sk_` key never reaches a bundle.
- All `@medusajs/*` packages on one version; `kekkai check @medusajs/medusa`
  before upgrading; `kekkai ./repo` after.

## The other half

kekkai asks what the site gives away. Its twin, `senrigan`, asks what the site
fails to tell search engines and LLMs — titles, canonicals, hreflang,
sitemap, structured data. Build by both rule sets; run both before release.

## When a rule and a feature collide

Prefer the rule. If the feature wins (a third-party embed, say), scope the
exception to one directive and one origin, write down *why* in the commit
message, not in a public file, and re-run `kekkai` so the exception is
visible as a deliberate warning rather than an accident.
